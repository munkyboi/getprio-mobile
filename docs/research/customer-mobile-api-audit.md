# GetPrio customer mobile API audit

Date: 2026-08-28  
Primary source: `/Users/carloabella/Projects/getprio/dev`  
Scope: customer-only queue flows for the Flutter mobile MVP. This is a source audit; no runtime behavior was exercised.

## Executive findings

The existing `/api/auth`, `/api/account`, and `/api/public` routes cover most of the customer MVP. Flutter can reuse the existing contracts for password registration/login, bearer-authenticated sessions, MFA enrollment and verification, vendor discovery, free queue joins, queue snapshots, ticket history, cancellation, and notification preferences.

Three confirmed mobile gaps remain:

1. OAuth completes by creating a browser session and redirecting to the web application's callback URL. There is no mobile bearer/deep-link completion path.
2. An authenticated direct join is deliberately rejected for paid queues; the existing paid path requires the OTP flow and returns to a web URL. That does not satisfy the authenticated-only mobile paid-join flow.
3. Push delivery is Web Push/VAPID only. There is no FCM device-token API or FCM delivery adapter.

These are the only findings in this audit that justify mobile-specific backend work. The audit does not recommend duplicating already-suitable shared endpoints under `/backend/mobile/`.

## Route base and authentication transport

The server mounts the route groups under `/api`: auth, account, public, push, and vendor are mounted in [`backend/src/app.ts:105-111`](/Users/carloabella/Projects/getprio/dev/backend/src/app.ts:105).

`authenticate` and `maybeAuthenticate` accept either a bearer token or the existing browser cookie session. The middleware reads `Authorization: Bearer ...`, rejects a request that sends both bearer and cookie authentication, validates the JWT's server-side session, and records the selected transport in `req.auth` ([`backend/src/middleware/auth.js:9-21`](/Users/carloabella/Projects/getprio/dev/backend/src/middleware/auth.js:9), [`backend/src/middleware/auth.js:38-105`](/Users/carloabella/Projects/getprio/dev/backend/src/middleware/auth.js:38)). A bearer-only mobile request therefore bypasses the browser CSRF branch, which runs only when an access or refresh cookie is present ([`backend/src/middleware/csrfProtection.js:48-60`](/Users/carloabella/Projects/getprio/dev/backend/src/middleware/csrfProtection.js:48)).

## Confirmed mobile-specific gaps

### 1. OAuth has no mobile bearer/deep-link completion contract

The provider start route creates server-side OAuth state and redirects to Google or Facebook. Both provider URLs use the server callback `/api/auth/oauth/:provider/callback` ([`backend/src/routes/authRoutes.js:439-452`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/authRoutes.js:439), [`backend/src/services/oauthService.js:94-120`](/Users/carloabella/Projects/getprio/dev/backend/src/services/oauthService.js:94)).

The callback exchanges the provider code, creates a session, calls `issueBrowserSession`, and redirects to `APP_BASE_URL + OAUTH_CALLBACK_PATH` ([`backend/src/routes/authRoutes.js:475-507`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/authRoutes.js:475), [`backend/src/services/oauthService.js:50-70`](/Users/carloabella/Projects/getprio/dev/backend/src/services/oauthService.js:50)). It does not pass the access/refresh tokens to a mobile deep link. Password login/register/refresh can return bearer tokens only when `AUTH_BEARER_COMPATIBILITY_ENABLED` is true and the request includes `X-Auth-Compatibility: bearer-v1` ([`backend/src/routes/authRoutes.js:173-190`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/authRoutes.js:173)); the setting defaults to enabled unless explicitly set to `false` ([`backend/src/config/env.js:105-118`](/Users/carloabella/Projects/getprio/dev/backend/src/config/env.js:105)).

**Required mobile decision:** add a narrowly scoped mobile OAuth completion/exchange contract under `/backend/mobile/`, or make the shared OAuth callback support a validated mobile redirect mode. It must return the same bearer-session contract through a verified deep link without placing refresh tokens in a URL. The existing provider start, state validation, provider exchange, and user creation logic should remain shared.

### 2. Authenticated paid joining is not exposed as a mobile-compatible flow

The direct join handler explicitly rejects any queue with a fee and returns `409` stating that verification is required before payment ([`backend/src/services/queueJoinPaymentService.js:359-369`](/Users/carloabella/Projects/getprio/dev/backend/src/services/queueJoinPaymentService.js:359)). The alternate shared route is `join-otp`; it verifies an OTP and then either creates a free ticket or creates a hosted PayMongo checkout ([`backend/src/routes/publicRoutes.js:706-755`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/publicRoutes.js:706), [`backend/src/services/queueJoinPaymentService.js:344-356`](/Users/carloabella/Projects/getprio/dev/backend/src/services/queueJoinPaymentService.js:344)). That is the existing guest/OTP flow, not the settled authenticated-only mobile flow.

The hosted checkout's success and cancel URLs are hard-coded to web routes under `CLIENT_URL` (`/ticket/...` or `/join/...`) with `payment` and `payment_status` query parameters ([`backend/src/services/queueJoinPaymentService.js:24-44`](/Users/carloabella/Projects/getprio/dev/backend/src/services/queueJoinPaymentService.js:24)). The existing sync endpoint can reconcile a known payment ID, but it does not provide a mobile return/deep-link contract ([`backend/src/routes/publicRoutes.js:757-771`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/publicRoutes.js:757)).

**Required mobile decision:** add a mobile-specific authenticated paid-join/checkout initiation contract under `/backend/mobile/`, or extend the shared contract to accept the authenticated customer and a validated mobile return target. The server must keep ticket issuance behind confirmed PayMongo payment; the existing webhook and sync logic are reusable ([`backend/src/routes/paymongoWebhookRoutes.js:7-23`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/paymongoWebhookRoutes.js:7), [`backend/src/services/queueJoinPaymentService.js:433-461`](/Users/carloabella/Projects/getprio/dev/backend/src/services/queueJoinPaymentService.js:433)).

### 3. FCM registration and delivery are absent

The current push API exposes a VAPID public key and authenticated Web Push subscription create/delete routes. The subscription service validates browser `endpoint`, `keys.p256dh`, and `keys.auth` fields ([`backend/src/routes/pushRoutes.js:7-12`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/pushRoutes.js:7), [`backend/src/routes/accountRoutes.js:454-498`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/accountRoutes.js:454), [`backend/src/services/pushNotificationService.js:30-59`](/Users/carloabella/Projects/getprio/dev/backend/src/services/pushNotificationService.js:30)). No FCM token route, Firebase sender, or mobile notification channel appears in the inspected backend source.

The queue outbox/worker is reusable as the delivery source: PostgreSQL outbox rows are claimed and retried, and the dispatcher currently handles `web_push` and email ([`backend/src/repositories/queueNotificationOutbox.js:7-35`](/Users/carloabella/Projects/getprio/dev/backend/src/repositories/queueNotificationOutbox.js:7), [`backend/src/services/queueNotificationOutboxDispatcher.js:107-146`](/Users/carloabella/Projects/getprio/dev/backend/src/services/queueNotificationOutboxDispatcher.js:107)). Existing queue customer notification coverage includes cancellation, near-turn, close/reopen, skipped, called, served, requeued, and carried-over events in the web-push execution checklist ([`docs/plan/web-push-notifications-execution-checklist.md:94-109`](/Users/carloabella/Projects/getprio/dev/docs/plan/web-push-notifications-execution-checklist.md:94)).

**Required mobile decision:** add mobile device-token registration/deactivation under `/backend/mobile/` and add an FCM delivery adapter/channel behind the existing outbox. The account's `queueAlerts` setting should remain the shared preference gate. FCM should be treated as a transport signal; the REST queue snapshot remains authoritative.

## Confirmed behavior versus risks/open questions

### Confirmed behavior Flutter can rely on

- Ticket status is the shared `TicketStatus` union: `waiting`, `pending_carry_over`, `called`, `served`, `skipped`, `cancelled`, `unserved`, and `expired` ([`shared/types.ts:1-18`](/Users/carloabella/Projects/getprio/dev/shared/types.ts:1)).
- A user-owned queue snapshot is protected by `customerTicketAccess`; an unauthenticated or different account cannot read another account's focus ticket ([`backend/src/routes/publicRoutes.js:454-470`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/publicRoutes.js:454)).
- Cancellation is only accepted for `waiting` tickets by the public route ([`backend/src/routes/publicRoutes.js:831-848`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/publicRoutes.js:831)).
- PayMongo ticket creation is after confirmed payment: the paid-payment activation creates the ticket and then records the payment's ticket ID/lookup code ([`backend/src/services/queueJoinPaymentService.js:433-461`](/Users/carloabella/Projects/getprio/dev/backend/src/services/queueJoinPaymentService.js:433)).
- Push is best effort and queue state transitions are not dependent on successful Web Push delivery; the execution checklist explicitly records this behavior ([`docs/plan/web-push-notifications-execution-checklist.md:128-136`](/Users/carloabella/Projects/getprio/dev/docs/plan/web-push-notifications-execution-checklist.md:128)).

### Risks/open questions, not new-endpoint findings

- `AuthResponse` makes bearer tokens optional because the same response serves browser and compatibility transports. Flutter must send the bearer compatibility header on password login/register/refresh/MFA completion and must not depend on cookies ([`backend/src/routes/authRoutes.js:173-190`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/authRoutes.js:173), [`shared/types.ts:1470-1485`](/Users/carloabella/Projects/getprio/dev/shared/types.ts:1470)).
- `/api/account/overview` is capped at 50 tickets, while `/api/account/history` is paginated. The mobile client should use history for the complete My Tickets list ([`backend/src/routes/accountRoutes.js:291-306`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/accountRoutes.js:291), [`backend/src/routes/accountRoutes.js:688-699`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/accountRoutes.js:688)).
- The account formatter reports `mfaRequired` from the stored field only, while `/api/auth/me` also derives it from privileged roles. This is a confirmed shared response inconsistency for mixed-role accounts, but it does not require a mobile endpoint and is not material for ordinary customer accounts ([`backend/src/routes/accountRoutes.js:265-277`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/accountRoutes.js:265), [`backend/src/routes/authRoutes.js:260-273`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/authRoutes.js:260), [`backend/src/services/mfaService.js:107-112`](/Users/carloabella/Projects/getprio/dev/backend/src/services/mfaService.js:107)).
- The existing SSE queue stream sends full snapshots and supports optional ownership checks, but it is a browser-oriented transport in the current frontend. It is not needed as a new mobile endpoint if FCM signals cause Flutter to refetch the authenticated REST snapshot; the route is documented here for completeness ([`backend/src/routes/publicRoutes.js:873-934`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/publicRoutes.js:873), [`frontend/src/pages/CustomerDashboardPage.tsx:123-145`](/Users/carloabella/Projects/getprio/dev/frontend/src/pages/CustomerDashboardPage.tsx:123)).
- The public vendor profile includes location contact fields in its shared type. The mobile UI should expose only the customer-directory fields approved by product/privacy review, but the audit found no confirmed need for a separate mobile directory endpoint ([`shared/types.ts:1536-1550`](/Users/carloabella/Projects/getprio/dev/shared/types.ts:1536), [`backend/src/routes/publicRoutes.js:151-183`](/Users/carloabella/Projects/getprio/dev/backend/src/routes/publicRoutes.js:151)).

## Recommended boundary

Reuse the shared API for all rows marked **Reuse**. Reserve `/backend/mobile/` for:

- validated mobile OAuth completion and bearer/deep-link handoff;
- authenticated paid queue-join initiation plus a mobile-safe hosted-checkout return contract; and
- FCM device-token lifecycle and outbox delivery integration.

No other mobile-specific endpoint is justified by the inspected source. Flutter models should be generated or maintained from the shared contract shapes rather than changing backend responses during the initial client build.
